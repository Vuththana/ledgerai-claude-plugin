# SDD conventions

Every `/sdd:*` command and every sdd agent follows these. The formats themselves are defined **only** in the docs repo's `specs/_templates/` — read the template before writing or checking a file of that kind. Never restate a template from memory.

## 1. The docs root

`ledgerai-project-docs` is the source of truth. Find it in this order and use the **absolute path** from then on:

1. A path you were given, or the current directory if it has `specs/README.md`.
2. In a workspace folder (the repos are subfolders): the subfolder that has `specs/README.md` (e.g. `ledgerai-project-docs/`, or the `<project>-docs/` that `/sdd:init` creates). If several do, ask which one.
3. In a code repo: `docs/` — **read-only** (it's a submodule pinned to a version).
4. Otherwise ask the user where a clone is.

A docs root is SDD-ready when it has `specs/README.md`. If it doesn't, stop and suggest `/sdd:init`, which adds `specs/` to existing docs.

**Writing to the docs** happens only in a separate clone (2 or 4), never in a `docs/` submodule, and only on a branch: `spec/<feature>` for specify / clarify / amend / migrate, `feature/<feature>` for plan / tasks / trace / API reference entries. Create a missing branch from `origin/main` (`git fetch` first). Reuse the branch if it exists. Before switching, if the clone has uncommitted changes, ask the user. Commit with a `VERSION.md` entry (format in `VERSION.md`). **Never push** without the user's approval.

## 1b. Code repos work on `dev`, never `main`

In the implementation repos (web-ui, the Spring services, ai-service):

- Feature branches (`feature/<feature>`) start from `origin/dev`. Pull requests go **into `dev`**.
- **Never commit to, push to, or merge into `main`**, and never open a pull request against it. The user merges `dev` into `main`.
- Compare against `dev`: reviews, the secrets check, migration checks.
- A repo with no `dev` branch: stop and ask; don't fall back to `main`.

The docs repo and the plugin repo are not code repos: they keep working against `main` (§1).

## 1c. web-ui milestones: M1 static UI, M2 integration

web-ui delivers every feature twice (`TEAM-RULES.md` § "web-ui: two milestones"): **M1** static screens with hardcoded placeholder data (50% deadline), then **M2** integration with the real API (100% deadline). The current milestone is the **Current web-ui milestone** line there; read it before building, verifying, testing or shipping web-ui work.

| | M1 — static UI | M2 — integration |
|---|---|---|
| Gate | spec ✅, plan approved, **every screen has its Figma frame** | the current milestone is M2 |
| `tasks.md` | `Phase 2 — web-ui static UI (M1)` | `Phase 3 — web-ui integration (M2)` |
| web-ui branch | `feature/<feature>` | `feature/<feature>-integration` |
| Review and QA | screens, states, wording, roles shown, Figma | everything, against the real services |

- Only the current milestone's web-ui tasks are built. A feature's M2 tasks wait until the team moves to M2, even when its M1 is done.
- Service tasks (Spring, ai-service) are not split: they're built as soon as the plan is approved, so the endpoints are ready for M2.
- In M1, the IDs only M2 delivers (data, submits, role enforcement, error codes, tests) are expected to be open. Don't report them as missing.

## 2. Where a feature lives

```
specs/README.md              index: every feature, its prefix, status, stage
specs/<feature>/spec.md      WHAT   (written by specify / clarify / amend / migrate)
specs/<feature>/plan.md      HOW    (written by plan, after Gate 1)
specs/<feature>/tasks.md     WORK   (written by tasks; ticked only by the lead session)
specs/<feature>/trace.md     generated by trace.py — never edited by hand
data-dictionary/  api/  TRD.md  TEAM-RULES.md  VERSION.md   shared, at the top
```

`<feature>` is a kebab-case slug (`branch-management`). Find a feature by slug, prefix or title in `specs/README.md`; if nothing matches clearly, list the features and stop.

## 3. IDs

Every spec has a 2–4 letter **prefix** (`BRN`). IDs are stable: **never renumber, never reuse**. A withdrawn item stays in place, struck through, with the reason: `~~BRN-R07~~ withdrawn in v5.3.0: …`.

| ID | What | Lives in |
|---|---|---|
| `BRN-R03` | Requirement — one testable sentence | spec §5 |
| `BRN-E02` | Edge case and its expected result | spec §7 |
| `BRN-D04` | Decision (settled) | spec §3 |
| `BRN-Q05` | Open question (becomes a `D` when answered) | spec §10 |
| `BRN-M01` | Message (code + text) | spec §6 |
| `T07` | Task | tasks.md |
| `BRN-R03-V1` | QA scenario for R03, kind C / V / M (correctness / validation / misuse) | qa-reports/ |

**Downstream code carries the ID** so `trace.py` can find it:

- Tests name the ID first: JUnit `@DisplayName("BRN-R03 rejects a taken branch name")`, Playwright / Vitest `test("BRN-R03 …")`, pytest `def test_brn_r03_…`. One test may name several IDs.
- Production code does **not** get ID comments (noise that rots). The reviewer locates the code; tests and QA prove it.
- Plan items and tasks list the IDs they cover.

## 4. Spec status

| Status | Meaning | Allowed |
|---|---|---|
| 📝 Draft | Has open `Q`s or proposals | specify, clarify, plan *questions only* |
| ✅ Approved | No open `Q`, auditor says ready, user approved | plan, tasks, build, verify, qa |
| ⟳ Amending | An approved spec being changed via `/sdd:amend` | build pauses for the stale tasks only |

**Don't build on a guess** (`TEAM-RULES.md` §6): nothing past `/sdd:plan` runs on a 📝 spec.

## 5. Severity — one scale everywhere

Reviewers, QA and audits all use:

- **Blocker** — security, another business's or branch's data, data loss, a missing requirement, a broken API contract.
- **Major** — a wrong rule, wrong error code, journey that can't be finished, missing state, a plan task not done, work outside the plan.
- **Minor** — a wrong message, naming, style, a missing audit row.

Plus **Spec gap**: something the code or test had to decide that the spec doesn't say. Gaps go to the user for `/sdd:amend` — never "fixed" in code.

## 6. Who edits what

| Who | Edits |
|---|---|
| Lead (the main session running a `/sdd:*` command) | specs/ and VERSION.md in the docs clone, tasks.md ticks |
| Developer agents | their own repo's code and tests only |
| Reviewer, auditor, planner, dictionary-checker agents | nothing (read-only) |
| QA agents | `qa-reports/` only |
| Nobody, ever | a `docs/` submodule; `trace.md` by hand; a ✅ spec outside `/sdd:amend` |

## 7. Scripts

The core plugin ships one deterministic checker, `sddtool.py` (Python 3 stdlib), in the `trace` skill's `scripts/` folder. From any sdd skill run it as `python3 -I "${CLAUDE_SKILL_DIR}/../trace/scripts/sddtool.py" …`:

- `check <docs-root> <feature>` — spec and tasks lint: duplicate or malformed IDs, references to undefined IDs, open `Q`s on a ✅ spec, R/E-IDs with no task, tasks citing unknown or withdrawn IDs, spec changed since the plan was approved.
- `trace <docs-root> <feature> <repo>…` — writes `specs/<feature>/trace.md` (`--no-write` to only print) and prints the summary, open IDs and drift.
- `status <docs-root>` — one table of every feature: spec status, open questions, plan, task progress, trace.

Exit code 0 = clean, 1 = findings, 2 = usage error. Trust the script over your own reading for anything it checks.

## 8. Agents see only what you pass them

When a command starts an agent: give absolute paths (docs root, each repo, the spec / plan / tasks file), pass briefs and findings word for word, and continue the **same** agent with SendMessage after the user answers its questions. An agent that fails twice: tell the user, don't do its work yourself.
