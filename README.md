# ledgerai-claude-plugin — LedgerVision v2 (Spec-Driven Development)

Claude Code plugins that take a LedgerVision AI feature from idea to shipped. Every requirement has an ID, and the trace follows that ID from the spec to its plan, tasks, tests and QA. Commands are `/sdd:*`. This v2 replaces the v1 plugins (`/ledgerai:*`, `/website-dev:*`, `/springboot-dev:*`), which are kept in git history.

## Why v2

v1 already worked spec-first (audit-flow → document-feature → dev-team → review → qa), but four things were missing:

| Gap in v1 | v2 |
|---|---|
| Flows were written by hand | `/sdd:specify` interviews you and writes a 📝 spec |
| You applied audit answers and approvals by hand (≈12 files per approval) | `/sdd:clarify` asks the open questions, applies the answers to the spec, dictionary and `api/`, and approves the spec |
| An approved plan went straight to developers | `/sdd:tasks` writes ordered, checkable tasks, and every task covers requirement IDs |
| Flows had no requirement IDs, so nothing linked a requirement to code, tests and QA | IDs (`BRN-R03`) run from the spec to the test name and the QA scenario, and `/sdd:trace` builds the matrix and finds drift |

It also fixes some v1 drift:

- The plan is defined in one place (`specs/_templates/plan.md`) instead of four.
- One severity scale (Blocker / Major / Minor) replaces two.
- One `check-secrets` skill replaces the two per-stack copies.
- One QA method replaces the repo-local `qa-tester` agents.
- One format for resolved questions and dictionary changes.
- A central message catalogue (`M` IDs).
- The separate analyst hop is gone, because the planner reads the structured spec directly.

## The flow

```
/sdd:init            → a new project's docs (specs/, data-dictionary/, api/, TRD, TEAM-RULES), or specs/ added to existing docs
/sdd:specify <idea>  → specs/<f>/spec.md 📝   requirement (R), edge case (E), decision (D), message (M), question (Q) IDs
/sdd:clarify <f>     → questions answered, dictionary and api/ updated → spec ✅            ⏸ you approve the spec
/sdd:plan <f>        → specs/<f>/plan.md (API contract, every item cites IDs)             ⏸ you approve the plan
/sdd:tasks <f>       → specs/<f>/tasks.md (T01…, per repo, [P] parallel, "after", "done when")
/sdd:build <f>       → api-dev / web-dev per repo, in parallel, by task ID; the lead ticks tasks.md
/sdd:verify <f>      → spec-reviewer ∥ dictionary-checker ∥ web-reviewer / api-reviewer → ≤2 fix rounds
/sdd:qa <f>          → api-qa then web-qa, one scenario set per ID (BRN-R03-V1) → qa-reports/
/sdd:trace <f>       → specs/<f>/trace.md: ID × plan × tasks × tests × QA, plus drift
/sdd:ship <f>        → check-secrets, summary                                              ⏸ you approve each push

/sdd:run <f>         plan → … → ship in one go, with both gates (replaces /ledgerai:dev-team)
/sdd:amend <f> <chg> change an approved spec first: new or withdrawn IDs, stale tasks marked ⟳
/sdd:migrate <flow>  v1 flow/<x>.md (+ saved plan) → specs/<x>/ with IDs, checked for faithfulness
/sdd:status          every feature: spec status, open questions, plan, task progress, trace
/sdd:review-pr [PR]  stack reviewer ∥ dictionary-checker (∥ spec-reviewer when the branch has a spec)
/sdd:sync-docs       is this repo's docs/ submodule behind, and what does it break (incl. withdrawn IDs)
/sdd:log [today|…]   where you are (project, branch, last SDD step per feature) and every prompt you typed
```

## Where things live

| Layer | Where | Holds |
|---|---|---|
| **What and why** | docs repo `specs/<feature>/spec.md` | Requirements with IDs, journeys, messages, edge cases, decisions, questions |
| **How** | `specs/<feature>/plan.md` | The approved plan for one spec version (the header records the spec commit, which is how drift is detected) |
| **Work** | `specs/<feature>/tasks.md` | Checkable tasks. Only the lead session edits it |
| **Proof** | `specs/<feature>/trace.md` | Generated by `sddtool.py`. Never edited by hand |
| **Shared** | `data-dictionary/`, `api/`, `TRD.md`, `TEAM-RULES.md`, `VERSION.md` | As in v1 |
| **Formats** | `specs/_templates/` | The only definition of each file's format |
| **Workflow rules** | `plugins/sdd/skills/conventions` | Docs root, IDs, statuses, severity, who edits what. Preloaded by every agent |
| **Repo rules** | each repo's `CLAUDE.md` and `.claude/rules/` | As in v1 (`/sdd-spring:setup-service` installs the SDD versions) |

### IDs

`BRN-R03` requirement · `BRN-E02` edge case · `BRN-D04` decision · `BRN-Q05` question (becomes a D) · `BRN-M01` message · `T07` task · `BRN-R03-V1` QA scenario (C / V / M).

- IDs are never renumbered or reused. Changing what an approved requirement means = withdraw its ID (strike it through) and add a new one, so old tests show up as drift.
- Tests put the ID first in their name, e.g. `@DisplayName("BRN-R03 …")`, `test("BRN-R03 …")` or `test_brn_r03_…`. That is how the trace finds them.
- Production code carries no ID comments.

### Writing to the docs

All edits happen in a separate clone of `ledgerai-project-docs` (in the workspace, the sibling folder), never in a repo's `docs/` submodule:

- `spec/<feature>` branches for specify / clarify / amend / migrate
- `feature/<feature>` branches for plan / tasks / trace / API entries

Skills commit locally. Nothing is pushed without your approval.

## The plugins

| Plugin | Enable in | Contents |
|---|---|---|
| `sdd` | every repo, and the workspace folder | 22 skills (17 commands plus `conventions`, `qa-method`, `identify-edge-cases`, `check-secrets`, `manage-dependencies` as auto / preloaded); agents `spec-auditor` (sonnet), `planner` (opus), `spec-reviewer` (sonnet), `dictionary-checker` (haiku); `sddtool.py`; **audit log hooks**: every prompt you type (secrets masked) and every action Claude takes (tool and target, never contents) go to `~/.claude/sdd-audit/`, and each session starts with "📍 Last time: <project> (<branch>) · last SDD step …" |
| `sdd-web` | web-ui | agents `web-dev`, `web-reviewer`, `web-qa`; `implement-feature`, `figma-design`, `debug-frontend`, test placeholders; ESLint hook; **package gate** hook (blocks installing a package with no Approved row in the team's Package Requests sheet, so Claude files the request under the member using it) |
| `sdd-spring` | Spring services | agents `api-dev`, `api-reviewer`, `api-qa`; `setup-service` (+ template), `implement-feature`, `add-migration`, `add-endpoint`, `write-tests`, `debug-backend`; compile-check hook |
| `sdd-fastapi` | ai-service | placeholder `ai-dev`, `qa-ai`, `ai-eval` (until the repo exists and TRD Q4 / Q21 are settled) |

Model and effort per agent follow v1's reasoning: opus only for the planner, haiku for the dictionary check, sonnet for the rest.

### sddtool.py

`plugins/sdd/skills/trace/scripts/sddtool.py` uses only the Python 3 standard library and is deterministic. Skills call it, and you can run it yourself:

```bash
python3 -I plugins/sdd/skills/trace/scripts/sddtool.py check  <docs> <feature>          # lint spec + tasks
python3 -I plugins/sdd/skills/trace/scripts/sddtool.py trace  <docs> <feature> <repo>…  # write trace.md
python3 -I plugins/sdd/skills/trace/scripts/sddtool.py status <docs>                    # every feature
python3 -I -m unittest discover -s tests                                                  # its tests + the package gate's
```

## Installing

Each LedgerVision repo enables its plugins in its committed `.claude/settings.json`. Copy the matching file from `templates/`:

| Repo | Template | Enables |
|---|---|---|
| web-ui | `templates/web-project-settings.json` | `sdd`, `sdd-web` |
| A Spring service | installed by `/sdd-spring:setup-service` | `sdd`, `sdd-spring` |
| The workspace folder that holds every repo (for `/sdd:run` across repos) | `templates/workspace-settings.json` | all four |
| Anything else (e.g. the docs repo) | `templates/project-settings.json` | `sdd` |

Then pull the repo, run `claude` in it, trust the folder, and accept installing the `ledgerai` marketplace and its plugins. `/plugin` should list them under **Installed**.

By hand:

```
/plugin marketplace add Vuththana/ledgerai-claude-plugin
/plugin install sdd@ledgerai
/plugin install sdd-web@ledgerai       # web-ui
/plugin install sdd-spring@ledgerai    # Spring services
```

The repo is private: you need read access on GitHub and a working login (`gh auth login`, or an SSH key).

**Updates:** `/plugin marketplace update ledgerai`, then restart Claude Code. A plugin's changes arrive only when its `version` in `plugin.json` goes up.

## Moving a repo from v1 to v2

1. **Docs:** the docs repo needs `specs/` on `main`. In a clone of `ledgerai-project-docs`, run `/sdd:init`: it adds the spec index and templates on a `sdd-setup` branch for a docs pull request.
2. **Each code repo:** replace the v1 plugin ids in `.claude/settings.json` (`ledgerai@ledgerai`, `website-dev@ledgerai`, `springboot-dev@ledgerai`, `fastapi-dev@ledgerai`) with the v2 ones from `templates/`. In a Spring service, re-run `/sdd-spring:setup-service`.
3. **Features:** `/sdd:migrate all` lists the v1 flows; migrate each one before it's next built.
4. **Tests:** rename tests to start with the requirement ID they prove, so `/sdd:trace` counts them.
5. **Then:** point `TEAM-RULES.md` §3 and §6 at `specs/` in a docs pull request.

A new project with no docs yet starts with `/sdd:init` in an empty folder.

## Changing the plugins

The same rules as v1:

- What a feature does lives in the docs. How code is written lives in each repo's rules. Steps live in skills.
- Skills point to the docs and never restate them.
- Bump `version` in the changed plugin's `plugin.json`, then run `claude plugin validate` on the marketplace and each plugin, plus the unit tests above.

| Plugin | Version | Change |
|---|---|---|
